# 错误重试分层策略（步骤 4/8/9/自动运行）

本文档说明当前实现中的三层重试语义，避免把“当步重试 / 小循环重试 / 大循环重试”混在一起理解。

## 1. 第一层：当步重试（Step 内部）

定义：不离开当前步骤，在当前页面链路内恢复或替换资源。

典型位置：
- `background/steps/fetch-signup-code.js`（步骤 4 页面恢复）
- `background/steps/fetch-login-code.js` + `background/verification-flow.js`（步骤 8 邮箱轮询与重发）
- `background/phone-verification-flow.js`（步骤 9 号码轮换、重发、回到 add-phone）

常见动作：
- 点击 `Try again` 恢复 405/重试页；
- 同一步内重新拉验证码；
- 步骤 9 内直接换号（不立刻回步骤 7）；
- 同提供商/同国家内换价格档位或换号码。

## 2. 第二层：小循环重试（授权链路重开）

定义：当前轮次内回到授权链路起点（通常步骤 7），再走 7→8→9。

触发来源：
- `background.js` 的 `getPostStep6AutoRestartDecision(...)`；
- 步骤 8 检测到邮箱通信异常且当前链路连续重试超限；
- 步骤 9 触发 `PHONE_RESTART_STEP7` 类错误（例如回调窗口过期/链路不可恢复）。

特点：
- 还是同一“轮次”；
- 不进入线程间隔（20 分钟）；
- 优先用于“流程状态错位/页面链路失效”类问题。

## 3. 第三层：大循环重试（自动运行 attempt/round）

定义：由自动运行控制器决定是否进入下一次 attempt，或等待线程间隔后继续。

位置：
- `background/auto-run-controller.js`

关键点：
- `autoRunSkipFailures=true` 时，允许同轮多次 attempt；
- 某些错误会被视为“本轮直接失败并跳过剩余重试”；
- 若配置了线程间隔，会出现“等待 N 分钟后第 x 次尝试”日志。

## 4. 错误分类优先级（当前实现）

1) 先做当步恢复（能在步骤内闭环就不升级）
2) 当步失败后，再判断是否走小循环（回步骤 7）
3) 小循环仍失败，才交给大循环（attempt / round / 线程间隔）

## 5. 已落实的关键规则（与近期问题对应）

- `Failed to fetch / network error / fetch failed`：
  步骤 4/8/9 进入有上限的网络重试（当前默认 3 次，冷却 12 秒）。

- `Step 9: 5sim check activation failed: order not found`：
  归类为“号码失效”，在步骤 9 内立即换号（当步重试），不应直接触发线程间隔。

- `Route Error 405`（手机号验证码页）：
  优先当步恢复；若落入 route-405 循环，步骤 9 内换号。

- `add-phone / phone-verification` 页面状态：
  表示流程已进入手机链路，自动运行层默认不再盲目回步骤 7，避免破坏当前链路。

- `Step 5` 启动时仍卡在 `/email-verification`：
  先在内容脚本内等待页面自行切换；如果识别到认证重试页则优先自动点击 `Retry / 重试` 恢复。若超过上限仍未退出邮箱验证码态，则抛出专用 `STEP5_STALE_SIGNUP_VERIFICATION` 错误，自动运行直接结束当前轮并进入下一轮，不再把它当成普通“未找到姓名输入框”的可重试失败。
  同时，当前注册邮箱会按“旧邮箱/已消耗邮箱”处理，从新注册邮箱池淘汰，避免后续轮次再次复用同一个 Hotmail。

- `Step 2` 提交邮箱/手机号后命中 `rate_limit_exceeded / 请求过多`：
  归类为注册身份限流错误 `SIGNUP_IDENTITY_RATE_LIMIT`。这类页面不再落成普通“等待页面跳转超时”，而是直接结束当前轮并进入下一轮，避免在同一风控页上空等。

- `account_deactivated / 账号已删除或停用`：
  无论是在步骤 2 入口切换后、步骤 4 提交验证码后，还是步骤 5 进入资料页前才暴露出来，只要认证页明确出现 `account_deactivated` 或“该账户已被删除/停用”文案，都会直接抛出专用 `SIGNUP_ACCOUNT_DEACTIVATED` 错误。自动运行收到后会立即结束当前轮、标记当前注册邮箱不可用，并进入下一轮，不再落成 `Step 5` 残留或“未找到姓名输入框”。

- `identity_provider_mismatch / 身份验证方式冲突`：
  只要注册链路任意阶段明确出现 `identity_provider_mismatch` 或“请使用注册时使用的身份验证方式重试”，都会按“当前注册邮箱不可再复用”处理。自动运行会直接结束当前轮、淘汰当前邮箱并进入下一轮；不会再在 `fetch-signup-code` 节点里沿用同一个邮箱回到 `open-chatgpt` 重开。

- `PLUS_CHECKOUT_NON_FREE_TRIAL / 没有免费试用资格`：
  这类错误同样会把当前邮箱标记为已消耗，后续“继续自动运行”也不会复用旧邮箱。
  但要区分两层语义：
  1. 当前轮一旦命中非 0 金额，当前 attempt 会立刻失败，不会在同一个邮箱上继续死等。
  2. 是否在同一轮里再开一个“新邮箱 attempt”，由侧边栏的“无试用套餐自动重试”开关控制；关闭时，本轮直接结束并进入下一轮/停止，开启时，会在同轮内换新邮箱再试一次。

- `already paid + add-phone` 窄恢复分支：
  仅当同时满足 `panelMode=sub2api`、`plusModeEnabled=true`、`phoneVerificationEnabled=true`、`plusAccountAccessStrategy=phone_bind_oauth` 时，如果步骤 6 已确认账号本身就是 Plus，且后续 OAuth 进入 `add-phone`，自动运行允许跳过重复 Checkout，回到手机补绑尾链路继续执行 `post-login-phone-verification -> confirm-oauth -> platform-verify`。
  该分支不会放宽到普通新注册、普通 OAuth、CPA、Codex Session 或其他支付路径。

- `sub2api` 远端写入去重：
  当同邮箱账号已经是 Plus 且链路已能直接推送到 `sub2api` 时，平台回调提交前会先查询同邮箱的远端 `openai/oauth` 账号；`error` 状态账号会优先删除；如果已存在存活账号，则直接更新并复用这一条，同时尽量删除其余重复存活账号，只保留一个远端账号。

## 6. 关于“第几轮尝试 + 暂停”含义

- “第 x/y 轮第 n 次尝试”是自动运行控制器的外层 attempt 计数；
- “线程间隔：等待 20 分钟...”表示已经升级到第三层（大循环）；
- 用户手动停止会中断当前计划；恢复时是否回到步骤 7，取决于当前页面状态与回调是否过期：
  - 回调未过期且仍在可恢复链路：优先当前链路继续；
  - 回调已过期或链路断裂：回步骤 7 重拉授权。

- 但如果上一轮失败已经能明确说明“当前邮箱已是旧邮箱/已消耗邮箱”（例如 `STEP5_STALE_SIGNUP_VERIFICATION`、`SIGNUP_IDENTITY_RATE_LIMIT`、`SIGNUP_ACCOUNT_DEACTIVATED`、`user_already_exists`、`identity_provider_mismatch`、无试用资格、已是 Plus），则“继续自动运行”不会再从旧节点原地续跑，而是改为从首个节点重新开始，并重新分配新邮箱。

- 上述这类“当前邮箱已废”错误在自动运行控制器层也会统一触发本地邮箱淘汰标记：
  当前 `Hotmail / Outlook`、别名邮箱、自定义邮箱池等会先标记为已消耗/不可复用，再进入下一轮，避免出现“日志看起来在跑新一轮，但实际反复拿到同一个旧邮箱”的情况。

## 7. SUB2API 老号存活同步刷新模式

这是一个独立于注册/自动运行主链路的侧边栏模式，只在：
- `导出至 = SUB2API`
- 开启 `老号刷新`
- 手动点击 `开始刷新`

时才会执行。它不会挂到现有自动注册 workflow，也不会改变当前注册流程的节点编排。

当前逻辑：
- 先拉取远端全部 `platform=openai`、`type=oauth`、`status=error` 的账号；
- 按邮箱去本地 `Hotmail` 号池精确匹配；
- 本地未找到：不删除远端，只记录到“本地未找到”列表；
- 本地找到但无法完成认证配置：删除对应远端 `error`，记录到“删除失败号”列表；
- 本地找到且能重新认证，并确认当前会话是 `Plus`：继续走 `confirm-oauth -> platform-verify` 尾链路覆盖同步到远端，记为“复活成功”；
- 本地找到但确认不是 `Plus`：同样删除对应远端 `error`，避免远端残留无效错误号。

侧边栏统计项：
- `总 Error`：本轮从远端拉到的 `error` 总数
- `已刷新`：本轮已处理的条数
- `复活成功`：本轮成功重新同步到远端的条数
- `删除失败号`：本地命中但无法完成有效复活、因此已删除远端 `error` 的条数
- `本地未找到`：远端有 `error`，但本地邮箱池找不到映射邮箱的条数
- `复活比`：`复活成功 / 总 Error`
- `当前邮箱`：当前正在处理的邮箱

侧边栏结果区：
- 会额外展示“最近一轮”摘要；
- 会展示本地 helper 快照路径；
- 会保留“全部 error 条目状态”列表，按条显示每个远端 error 邮箱当前是：
  - `待刷新`
  - `本地未找到`
  - `已复活`
  - `已判死`
- 会直接列出最近一轮的：
  - `本地未找到`
  - `已删除远端 error`
  - `已复活同步`

本地落盘：
- Chrome 本地存储：`sub2apiErrorRefreshHistory`
- 本地 helper JSON 快照：`data/sub2api-error-refresh-history.json`

落盘结果会保留每轮明细，包括：
- 最近一轮全部远端 `error` 条目及其最终状态，避免处理后直接从界面消失
- 哪些邮箱本地未找到
- 哪些邮箱已删除远端 `error`
- 哪些邮箱已成功复活并重新同步

说明：
- `Chrome storage` 与本地 helper JSON 快照都会保留 `allEntries`；
- 即使是旧历史、或只写入了部分 `allEntries` 的历史，也会在读取/同步时自动用 `details` 回填补齐，保证“全部 error 条目状态”列表尽量完整。
