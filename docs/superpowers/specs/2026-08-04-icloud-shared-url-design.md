# iCloud 共享 URL 导入设计

## 目标

让统一邮箱队列接受并轮询以下 iCloud 共享取信 URL：

```text
邮箱----https://icloud-api.top/s/共享标识/邮箱
```

本改动不改变 Outlook、已有 `icloud-api.top/show` 或任意域名 `/messages` 的导入和验证码逻辑。

## 方案选择

采用专用 HTTPS 路径白名单：仅 `icloud-api.top` 的 `/s/{token}/{email}` 加入与 `/show/{token}/{email}` 相同的受信任 URL 规则。

不把 `/s/` 放入通用域名规则，也不接受 HTTP 版本。共享标识具备取信能力，固定站点仅接受 HTTPS 能避免把该标识暴露给网络中间人；通用站点的 HTTP 支持仍只适用于既有 `/messages/` 格式。

## 导入与安全边界

- URL 必须有且仅有 `s`、非空共享标识、非空尾部邮箱三个路径段。
- 尾部邮箱 URL 解码、规范化后必须等于行首邮箱。
- 拒绝用户名、密码、显式端口、查询参数、片段、本机名及 IP 字面量。
- 已有 `/show`、通用 `/messages` 与 yangyang 两行续接格式保持不变。

## 取信

请求前与响应后都复用同一受信任规则。最终响应必须仍为 `https://icloud-api.top`，且路径仍以 `/s/` 开头，才能读取正文。页面正文继续交给现有验证码解析器；如果没有六位验证码，原有轮询重试与脱敏日志不变。

## 测试与验收

1. 批量导入中 `/s/` 记录能生成 `icloud-url` 队列项。
2. 传入 HTTP、错误路径、尾部邮箱不匹配的 `/s/` 记录被拒绝。
3. `/s/` 凭据页的站内 `/s/` 响应可提取六位验证码。
4. `/s/` 响应跳转到 `/show/`、`/messages/`、其他协议或域名时，在读取正文前拒绝。
5. 现有导入和 URL provider 全量测试、JavaScript 语法检查通过。
